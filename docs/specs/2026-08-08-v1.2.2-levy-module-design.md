## 1. 背景与目标

### 1.1 业务背景

v1.2.2 之前，项目中的「项目管理」模块只包含**调查业务**的录入、审核、导出（住户信息表、土地信息表等调查类动态表单，通过表单设计器自定义，配合 Excel 导出模板）。

征收作为土地/房屋征收工作的**后半阶段**，是调查阶段的业务延续（调查解决"摸清楚有什么"，征收解决"怎么签协议、补偿多少、怎么安置"），不能作为独立业务存在，必须在调查数据的基础上展开。

### 1.2 v1.2.2 需要交付的 4 项核心能力（用户原始需求）

> 以下 4 条摘自用户本会话原始需求原文，作为验收基准：

1. **调用调查数据生成打印文件**：征收业务中调出调查数据，生成 Word / Excel 文件（补偿协议、结算单、安置确认单等），用于打印归档。
2. **调查数据新增/修改**：征收阶段可能需要补充一些调查阶段没有的数据（征收专属字段），允许在征收模块里对调查数据做增量补充或修改。
3. **征收数据变更必须审批**：在征收功能里**新增或修改数据都不能直接生效**，需要经过配置的审批流程审批之后，才能正式写入正式数据表。
4. **全量操作可审计 + 超管统一查询**：调查和征收的所有审批与修改记录都必须**可追溯**，且由**超级管理员（ADMIN）在统一的入口查询**（含差异回放）。

### 1.3 额外附带改造项（用户口头确认的升级项）

- 「项目分类」从扁平列表升级为**按业务模块分类**：调查（SURVEY）/ 征收（LEVY）/ 通用（BOTH），H5 项目列表顶 Tab 切换。
- 现有导出模板设计器（仅支持 Excel）**扩展支持 Word 模板**（所见即所得的 A4 富文本画布 + 双模块字段库）。
- 现有审批流程设计器（未正式投入使用）**整体重做**：可视化拖拽画布、会签/或签、条件分支、并行节点、加签/转办/抄送/超时。
- 角色权限从「按表一张一张配」升级为**模块→分类→表→操作 四级树形勾选**，自带全选/半选/复制模板能力。

### 1.4 验收总目标

- 所有征收类数据新增/修改「提交≠生效」，必须走完审批链才落库。
- 调查数据改动 → 自动通知关联的征收记录做快照比对 → 发起同步审批 → 批准后自动同步。
- 任意时刻超级管理员能在审计中心按 5 大分类 + 全维度筛选，看到每一条操作的前后差异与审批轨迹。
- 后期业务自定义征收表格（表单设计器）、自定义审批流程（审批设计器）、自定义打印模板（模板编辑器）都不依赖开发。

## 2. 方案概述（最终选择：方案B「调查/征收分类独立 + 关联字段」）

### 2.1 方案选择：项目分类模式（用户口头确认选择 B）

- 系统有两个独立的**顶级项目分类**：「调查模块」和「征收模块」，在分类表 `TableCategory` 上用枚举 `module` 区分。
- 调查模块下的表（住户信息表、土地信息表等）保持现有调查流程不变。
- 征收模块下的表（征收补偿协议、安置信息、资金发放等）是另一批数据表，通过**一种新的字段类型 `LEVY_RELATION`（征收关联字段）**关联到调查表（如住户/宗地编号），关联时**自动把调查配置映射的字段值填充到征收表单**（填充为快照式复制，填充后在征收侧改不会反向写回调查）。

### 2.2 业务流程全景（文字版）

1. **调查阶段**（现有能力）：调查员录入住户/土地 → 调查审批通过 → 数据进入调查正式库。
2. **创建征收记录**：征收经办员在征收模块「新增征收补偿协议」→ 在 `LEVY_RELATION` 字段选择关联的调查记录（如住户"张三"） → 配置里的 `fieldMapping` 自动把姓名、身份证、地址、面积、房屋类型等调查字段填充到征收表单的对应字段。
3. **征收编辑审批**：经办员补充/修改征收专属字段（补偿金额、签约日期、安置房等） → 点「保存并提交审批」 → 系统保存**变更前快照** + 发起 `APPROVAL_CATEGORY=DATA_EDIT` 审批流程 → 走到终点 APPROVED 时才把数据真正写入 `DataRecord` + 写入操作日志。
4. **调查数据变更通知**：如果调查侧后来把"张三"的面积从 89㎡ 复测成 92㎡ → 调查侧保存成功后，后端任务遍历 `LEVY_RELATION` 关联表 → 查出"张三关联的所有征收协议记录" → 计算配置映射字段的前后差异 → 保存 `SYNC_BEFORE` / `SYNC_AFTER` 双快照 → 生成 `DataSyncRequest(PENDING)` + 发通知给征收经办/审批角色。
5. **调查数据同步审批**：征收侧看到"有调查差异待处理" → 点开差异回放（前后并排对比 + Δ高亮） → 发起 `APPROVAL_CATEGORY=DATA_SYNC` 审批 → 审批通过后系统自动用新快照数据更新征收记录的对应字段 → 状态置为 `SYNCED` + 写审计日志。
6. **文书生成打印**：在征收记录详情 → "生成文书" → 选择已配置好的 Word/Excel 模板（如《征收补偿协议正式版v3》） → 后端合并调查字段快照 + 征收字段数据 → 渲染成 Word（或PDF预览） → 打印/下载 → 每一次操作写入 `DocumentGenLog`。
7. **审计**：超级管理员登录 Dashboard → 侧边栏「审计日志中心」→ 5 个 Tab 切换查看全部轨迹，任意操作支持前后差异回放。

## 3. 第一部分：数据模型变更（Prisma Schema）

### 3.1 CategoryModule 枚举（`TableCategory.module`）

```prisma
enum CategoryModule {
  SURVEY  // 调查分类（原住户/土地调查归入）
  LEVY    // 征收分类（新增：补偿协议/安置/资金发放等归入）
  BOTH    // 通用分类（后期放共用的字典/辅助表）
}
```

- **影响位置**：`TableCategory` 表增加 `module CategoryModule @default(SURVEY)`；H5 `/h5/projects` 和 Dashboard 项目列表页顶部新增 Tab 筛选。
- **默认值兼容老数据**：现有分类迁移时全部 `SET SURVEY`。

### 3.2 FieldType 新增 `LEVY_RELATION`（征收关联字段）

```prisma
// 在现有 FieldType 枚举中追加
enum FieldType {
  // … 原有 TEXT / TEXTAREA / NUMBER / DATE / DATETIME / SELECT / MULTISELECT /
  //   IMAGE / ATTACHMENT / PEOPLE / LOCATION / MONEY / FORMULA / DETAIL_TABLE /
  //   UNIQUE_ID / APPROVAL_STATUS / SURVEY_LOCATION / FLOOR_PLAN / SIGNATURE
  LEVY_RELATION  // ✨ v1.2.2 新增：征收→调查 的关联字段
}
```

- **配置参数**存在 `TableField.config.levyRelationConfig`（JSON）：

  ```ts
  interface LevyRelationConfig {
    surveyTableId: string;          // 关联的调查类表ID（必须 module=SURVEY）
    displayFieldId: string;         // 下拉时展示哪个字段，如"姓名/宗地编号"
    fieldMapping: Array<{           // 字段映射：选完调查记录后，把哪些调查字段值复制过来
      surveyFieldId: string;
      levyFieldId: string;
    }>;
    autoSyncOnSurveyChange: boolean;  // 调查数据变更时是否自动生成同步申请，默认 true
    requireApprovalForEdit: boolean;  // 关联后是否允许在征收表单里改这些填充值（默认 true = 改就触发审批）
  }
  ```

- **后端行为**：
  - 前端选完调查记录（`POST /api/levy-relation/survey-records` 选中一条）后，后端按 `fieldMapping` 取调查记录对应字段值，返回到前端自动填入征收表单。
  - 征收记录落库时，`LEVY_RELATION` 字段自身只存调查记录的 `recordId`，真正的调查字段值**复制**进征收字段自身存一份（快照式保存，保证后续即使调查字段改了征收也不立刻乱）。

### 3.3 新增 DataSnapshot 表（数据快照 & 差异）

> 用于：征收修改审批前 / 同步审批前 / 同步执行后 的每一次数据状态留存。

```prisma
model DataSnapshot {
  id            String          @id @default(cuid())
  // —— 归属关系 ——
  tableId       String          // 哪张表
  tableName     String
  recordId      String          // 哪条记录（DataRecord.id）
  module        CategoryModule  // SURVEY / LEVY
  // —— 元数据 ——
  snapshotType  SnapshotType    // EDIT_BEFORE / EDIT_AFTER / SYNC_BEFORE / SYNC_AFTER
  createdBy     String?         // User.id（系统自动=SYSTEM）
  createdAt     DateTime        @default(now())
  // —— 数据 ——
  rawData       Json            // 完整记录当时的 DataRecord.data
  diffData      Json?           // 相对上一次版本的增量差异 {old:{...}, new:{...}, addedFields:[], removedFields:[]}
  relatedApprovalId String?     // 关联的审批单 ID（如果有）
  relatedSyncId String?         // 关联的同步申请 ID（如果有）

  // 索引
  @@index([tableId, recordId, createdAt(sort: Desc)])
  @@index([relatedSyncId])
}

enum SnapshotType {
  EDIT_BEFORE    // 征收编辑审批前的原始状态（基线）
  EDIT_AFTER     // 审批通过后写入 DataRecord 的新状态
  SYNC_BEFORE    // 调查变更 → 征收待同步时，征收当前状态
  SYNC_AFTER     // 调查变更 → 同步执行后征收的新状态
}
```

### 3.4 新增 DataSyncRequest 表（调查→征收 同步申请）

```prisma
model DataSyncRequest {
  id            String           @id @default(cuid())
  // —— 关联关系 ——
  surveyTableId    String
  surveyRecordId   String        // 哪个调查记录触发了变更
  levyTableId      String
  levyRecordId     String        // 需要同步到哪个征收记录
  levyRelationFieldId String     // 由哪个 LEVY_RELATION 字段配置的映射
  // —— 同步内容 ——
  changedFields    Json          // 变更的字段清单 [surveyFieldId → {old,new, mappedLevyFieldId}]
  snapshotBeforeId String        // DataSnapshot(SYNC_BEFORE)
  snapshotAfterId  String?       // DataSnapshot(SYNC_AFTER)，执行后才写
  // —— 生命周期 ——
  status           SyncStatus    @default(PENDING)
  approvalCategory String        // 固定 DATA_SYNC，用于审批引擎区分
  approvalInstanceId String?     // 关联审批单
  approvedAt       DateTime?
  approvedBy       String?
  rejectedAt       DateTime?
  rejectedReason   String?
  executedAt       DateTime?
  // —— 审计 ——
  createdAt        DateTime      @default(now())
  createdBy        String?       // 一般是 SYSTEM 自动检测创建，但也支持手动触发
  auditNote        String?

  @@index([levyRecordId, status, createdAt(sort: Desc)])
  @@index([surveyRecordId, createdAt(sort: Desc)])
}

enum SyncStatus {
  PENDING       // 已生成，等待经办员点击"发起同步审批"
  IN_APPROVAL   // 审批中
  APPROVED      // 审批通过，等待执行或已标记通过
  REJECTED      // 驳回（驳回 reason 必填，需保留显示）
  SYNCED        // ✅ 已执行同步，最终态
  CANCELLED     // 经办员主动取消（如变更无需同步）
}
```

## 4. 第二部分：新版审批流程引擎（整体重做）

### 4.1 设计器重做（Dashboard 管理端）

- **左侧节点工具箱**（拖入画布即添加）：
  - 发起节点（默认 1 个，不允许删除）
  - 审批节点（SINGLE / COUNTERSIGN / ORSIGN）
  - 条件节点（带左右分支：`满足条件 → 走上级，不满足 → 走队长`）
  - 并行分支节点（两个审批人同时待办）
  - 抄送节点（通知，不处理）
- **中间画布**：拖拽式布局，节点间自动箭头连线；条件分支自动生成左右两岔；点击连线删除分支。
- **右侧属性面板**（选中节点显示）：
  - 节点名称 + 节点类型切换
  - 审批人来源：指定用户 / 指定角色 / 表单公式（例：部门负责人）
  - 审批方式：或签（一人同意即过）/ 会签（全部同意才过）
  - 权限：允许加签 / 允许转办 / 节点内可编辑字段子集
  - 超时：多少小时未处理 → 自动通过 / 自动驳回 / 仅发提醒
  - 通过后自动动作：改某个字段值 / 发通知给某角色 / 打标签
- **流程版本化**：`WorkflowStatusV2` = DRAFT（设计中）/ ACTIVE（已发布，新提交走它）/ DEPRECATED（不再新提交，运行中实例继续走）/ ARCHIVED；每张表可多版本并行。

### 4.2 运行时审批详情页

- 顶部：审批对象头信息（哪张表、哪条记录的标题）+ 进度状态徽标（审批中/已通过/已驳回）
- 中部：**流程时间轴**
  - 已完成节点：绿色打钩 + 处理人 + 意见 + 处理耗时
  - 当前节点：黄色圆圈动效 + "待 xx 处理" + 预计超时时间
  - 待处理节点：灰色轮廓
  - 条件分支：哪条分支真走了高亮，另一条灰掉
  - 加签/转办：虚线子节点注明"张三加签给李四"
- 底部：当前待处理人的操作栏（仅当前登录用户是节点处理人时启用）：
  - 通过 / 驳回（驳回必须填写不少于 5 字的理由）
  - 加签（临时加一个人排在自己之后）
  - 转办（把节点转给另一个人，保留痕迹）
  - 查看数据差异（打开前后对比弹窗，审批必须看过才能提交）
  - 审批意见输入框（纯文本 + 富文本可选）+ 附件上传（审批材料）

### 4.3 审批三大触发场景

| 场景 | category | 触发时机 | 审批通过后自动动作 | 驳回动作 |
|---|---|---|---|---|
| ① 征收新增/修改 | `DATA_EDIT` | 经办在征收记录点「保存并提交审批」 | 用 EDIT_AFTER 快照写入 DataRecord（替换原记录或插入版本字段）→ 写 OperationLog → 通知发起人 | 原数据保持不变 + 通知发起人 + 审批意见回显 |
| ② 调查→征收同步 | `DATA_SYNC` | 经办在同步列表点击「发起同步审批」或系统自动发起 | 执行同步逻辑（按 changedFields 用 newVal 写征收记录）→ 生成 SYNC_AFTER 快照 + DataSyncRequest.status=SYNCED + 记审计 | DataSyncRequest.status=REJECTED + 存驳回理由，下次再改还会再触发新的 |
| ③ 超管强制 | （不走 category） | 超管在审计中心点「撤回」/「作废」 | 按 snapshotIds 回滚 DataRecord 数据 + 记强制回滚审批痕迹 | - |

## 9. 非功能性要求 & 风险

### 9.1 兼容性 & 可回滚

- **数据库**：使用 Prisma migrate 新增字段/表（**不删除任何老字段老表**，包括老的审批相关表、老的 TablePermission），任何一步出问题迁移本身可 `prisma migrate resolve --rolled-back` 回退。
- **权限判定**：`permissionTree` 空时自动 fallback 到 `TablePermission`，新老数据共存一个版本，v1.2.3 再清理。
- **审批老实例**：`ApprovalInstance` 无 `category` 时默认 `DATA_EDIT`；新老流程版本并行（ACTIVE 老流程仍然能完成）。

### 9.2 性能 & 大数据量

- `DataSnapshot` 数据量大：按月分分区（PostgreSQL `PARTITION BY RANGE(createdAt)`，或后续按月归档到 `DataSnapshot_archive_*` 表）；查询快照必须带 `tableId+recordId` 命中复合索引。
- `DocumentGenLog`、`LoginLog`、`OperationLog` 同理，默认查询强制带时间范围。
- 同步检测 `LevySyncDetectorService` 异步执行（BullMQ 任务），不阻塞调查侧保存响应（调查保存 30ms + 同步检测后台跑 1s 也不影响用户）。

### 9.3 安全

- 所有审计接口（`/api/audit-logs/**`）硬编码 `@RequireRole('ADMIN')`，即使 `permissionTree` 配错也拦。
- 差异回放弹窗展示敏感字段（身份证/金额）：审计日志中心默认身份证**脱敏**显示，超管可点「显示明文」按钮（额外加一次二次确认，该点击单独再写一条 `OperationLog(action=AUDIT_SENSITIVE_VIEW)`）。
- 批量下载接口请求频控 + 下载链接 10 分钟过期。

### 9.4 风险清单

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| Word → PDF 预览依赖本地 LibreOffice | Docker 部署时没装会失败 | Dockerfile 加 libreoffice 安装（或 fallback 不预览直接下载 Word）；给用户一条提示若预览失败直接下载；接口分两条，preview 依赖可选 |
| 审批引擎重做后，旧实例如何跑完 | 运行中审批错乱 | 老流程继续走旧 nodeIds 判定，新画布版只对新创建的 ACTIVE 流程启用 |
| 调查数据频繁修改导致同步审批炸了 | 审批人烦 | 自动同步申请可配置「同一字段 X 小时内只生成 1 条」合并窗口；相同记录的未处理 PENDING 同步请求合并覆盖 |
